# Technical decisions

| Choice | Reason and tradeoff |
|---|---|
| Synchronous SQLAlchemy | Keeps request and worker code straightforward. Synchronous demo requests wait for provider calls; queue ingestion is optional. |
| Policy rows with JSON rules | Exact refund thresholds need direct lookup, not vector retrieval. |
| Ordered workflow rows | Existing step types are configured as data; new behavior still needs Python support. |
| UUID keys | Stable identifiers generated by the ORM on insert/flush. They do not replace authorization checks. |
| VARCHAR enums | Store enum values without native PostgreSQL enum migrations. Validation is in the application; no enum CHECK constraints are generated. |
| Database-only mock effects | Makes a credential-free demo possible. A real connector would need implementation and stronger delivery guarantees. |
| Refund-specific approval resume | Preserves the focused reference workflow. General continuation would increase scope. |
| Celery and Redis | Preserve the existing queue and periodic retry setup. Durability requires more than simply selecting these tools. |
| Per-organization ingestion lock | A small way to serialize duplicate submissions; limits throughput within one tenant. |
| Direct backend dependency pins | Readable dependency list. Transitive versions are not fully locked. Frontend versions use an npm lockfile. |

The current review deliberately retains the original models, workflow runner,
provider interface, and frontend structure. Unimplemented schema fields are left
in place to avoid unnecessary migrations; their presence is not a feature claim.
